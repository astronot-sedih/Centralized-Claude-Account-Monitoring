# Centralized Claude Monitoring — Plan Overview

**Spec:** `docs/superpowers/specs/2026-10-28-centralized-claude-monitoring-design.md`
(Spike 0 passed — §0.0.1. Read the spec before any task; it carries the
constraints every plan assumes.)

This work is deliberately split into seven small plans rather than one large
one. Each produces working, independently testable software and can be
reviewed, committed and shipped on its own. Later plans consume earlier ones
through the interfaces named in their headers.

Plan 04 is independent of 01–03 and could run earlier or in parallel, but the
spec (§2.6) makes it a correctness prerequisite for plans 05–07: without it,
every per-person number in the report names the wrong person. Plan 07 Task 3
provides the UI for the flags plan 04 introduces, so 04 must land first.

Each plan is small enough to execute in one sitting: 2 tasks (01, 02), 3 tasks
(03, 04), 4 tasks (05, 06, 07).

## Tracker

Progress lives in SQLite so a session that loses context can recover it from
disk rather than from a summary:

```bash
node tools/monitoring-tracker/tracker.mjs recall        # start here, always
node tools/monitoring-tracker/tracker.mjs import docs/superpowers/plans/2026-10-28-01-units-and-severity.md
node tools/monitoring-tracker/tracker.mjs next
node tools/monitoring-tracker/tracker.mjs start 01-units-and-severity/1
node tools/monitoring-tracker/tracker.mjs done  01-units-and-severity/1 --commit <sha>
node tools/monitoring-tracker/tracker.mjs block 01-units-and-severity/2 "why"
node tools/monitoring-tracker/tracker.mjs decide "what" "why"
```

`recall` prints task counts, the spec and plan paths, every recorded decision,
recent notes, and what to do next. Run it first in any fresh session.

The plans are the source of truth for *what* the tasks are; the tracker holds
*status* plus the decisions and notes that would otherwise exist only in a
transcript. Record a decision whenever you resolve something the plan left
open — that is the part a future session cannot reconstruct.

## Global Constraints

These apply to every task in every plan. Values are copied from the spec.

- **Claude only.** Every query filters `provider === "claude"`. No other
  provider is collected, reported, or touched — not codex, gemini, glm, kiro,
  antigravity, none of the 40+. The `quotaSnapshots.provider` column exists so a
  later plan *could* widen this, but no task in these plans may read or write a
  non-Claude row. A monitor-only flag or a key pin set on a non-Claude
  connection is out of scope: implement the mechanism generically where it is
  cheaper to do so (it lives in shared selection code), but test and verify
  Claude only.
- **Every UI task MUST use BOTH design-system sources.** They answer different
  questions and neither is sufficient alone:
  1. **The MCP** — `http://10.1.11.153:1000/mcp` (plain HTTP; the `https://`
     form fails TLS, the server does not speak it). Tools:
     `list_components`, `search_components`, `get_component_specs`. Use it for
     **component APIs and semantics**: which component already covers the need,
     its real props/emits/slots, its variant vocabulary. It exposes **no design
     tokens** — there is no token or theme tool.
  2. **The DS source** — `C:/Users/rafli/Documents/Kerjaan/DDD/dakara-ds`. Use
     it for **actual values and CSS**: `tokens.css` (the `--sev-*`, `--sb-*`
     ramps, light block then dark block), `colors_and_type.css` (the
     `color-mix` derivations for `-soft` / `-line` / `-text`),
     `components/components.css` (how each `ds-*` class composes them),
     `DESIGN-SYSTEM.md` and `SKILL.md`.

  Read the token you need from the source rather than approximating it; a hex
  that merely looks right is off-brand and nobody will notice until the brand
  ramp moves. Already resolved in `src/lib/monitoring/tokens.js`: `SEV_TOKENS`
  (flattened hex, email) and `SEV_CSS_VARS` (live `var(--sev-*)`, dashboard) —
  reuse them, do not re-derive.

  The MCP serves **Vue/Nuxt** components, which cannot be imported into either
  target (email HTML, React dashboard), so components are **mirrored**:
  structure and semantics copied, code hand-written. The CSS, by contrast, is
  real and can be read verbatim.

  Applies to: Plan 05 Tasks 3–4 (email renderers) and Plan 07 Tasks 2–3
  (dashboard page and controls). Record what you used:
  `node tools/monitoring-tracker/tracker.mjs note <ref> "mirrored: <Component>; tokens: <file>"`
- **Plain JavaScript (ESM), no TypeScript.** `@/*` → `src/*` (`jsconfig.json`).
- **Never hardcode role/block/model strings** — use `open-sse/translator/schema/`
  and `open-sse/config/` constants.
- **Do not touch the routing hot path**: `open-sse/handlers/chatCore.js`,
  executors, translators. Plan 04 touches *account selection* only, inside the
  existing filter in `src/sse/services/auth.js`.
- **Preserve `custom-server.js` IP handling** — it derives client IP from the
  TCP socket and strips attacker-controlled `X-Forwarded-For`. No new route may
  trust a forwarding header.
- **Tests:** vitest, under `tests/`, its own ESM package. Run with
  `cd tests && npx vitest run <path>`; ignore the committed `test` script (it
  hardcodes Unix paths). The suite is **not green on a plain checkout**
  (~938 pass / ~64 fail, catalogued). Judge regressions with
  `tests/__baseline__/verify-no-regression.mjs`, never a raw run.
- **Severity comes from the API, not from our thresholds** (spec §4.2). Use
  `limits[].severity` and `limits[].is_active` when present; our 90/75/50 map is
  a fallback only.
- **`units`, not raw tokens**, is the measured quantity (spec §0.0.2):
  `cache_creation×1.25 + cache_read×0.1 + input×1 + output×5`.
- **USD only.** No currency conversion, no seat-price math (spec §2.5).
- **Unmeasurable cells read `"tak terukur"`** — never blank, never `0`, never
  `—` (spec §4.1).
- **Never fabricate a quota window the API did not return** (spec §3 anti-goals;
  existing comment in `open-sse/services/usage/claude.js`).
- **Tokens never leave the process**: no access/refresh token in any report,
  email, API response, log line, or persisted error string. Scrub before
  persisting (spec §7).
- **No monitoring code path may call `consumeClaudeResetGrant`** — it spends an
  irreversible, limited resource (spec §7).
- **Feature ships disabled** (`MONITOR_ENABLED=false`).
- **Commit style:** Conventional Commits (`feat(monitoring): …`,
  `fix(monitoring): …`). Log changes in `CHANGELOG.md`.
- **Commit messages end with:**
  `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`

## Review Focus

Input classes the spec implies that are most likely to bite a real user. Each
is pinned by a test in the plan that owns the code — named here once so none is
lost between plans.

1. **A quota window the API omits entirely** (`seven_day_opus: null` was
   observed). Must render as absent, not `0%` — a fabricated 0 reads as "plenty
   of headroom". → Plan 01, Task 2.
2. **An account whose token is expired or whose refresh fails.** Must be
   persisted as a failed read (`ok = 0`) and shown as unknown, never as 0% use —
   and must not abort the other ten accounts. → Plan 03, Tasks 2 and 3.
3. **A 429 from the usage endpoint across 11 sequential accounts.** Must not
   hammer, must not crash the run, must reuse the service's cooldown. → Plan 03,
   Task 3.
4. **A key pinned to a connection that is exhausted or monitor-only.** Must fail
   closed with a clear error, never silently spend a different teammate's quota
   — that is what corrupts attribution. → Plan 04, Tasks 2 and 3.
5. **A reporting day with partial sampling** (laptop asleep). Coverage must be
   stated in the report; a trend computed from 40% coverage presented as fact
   would mislead a budget decision. → Plan 05, Task 2 (and Plan 06, Task 2 for
   the catch-up send).
